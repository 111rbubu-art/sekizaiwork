# 勤怠管理システム 設計書

**プロジェクト**: sekizaiwork / 勤怠管理アプリ（`kintai`）
**作成日**: 2026-08-04
**対象**: 出退勤打刻（位置記録付き）・有給休暇管理・管理者集計

## 0. サマリー

| 項目 | 方針 |
|------|------|
| 打刻 | ブラウザの大ボタン1タップ。出勤／退勤／休憩開始／休憩終了 |

| 有給 | 労基法39条準拠（自動付与・比例付与・2年時効・FIFO消化・年5日取得義務アラート） |
| 配信 | 既存と同じ GitHub Pages / Netlify（静的ホスティング） |

### 2.1 なぜこの構成か（技術選定）

| 案 | 初期コスト | 月額 | 改ざん耐性 | 既存資産活用 | 判定 |
|----|-----------|------|-----------|------------|------|
| **A. SharePointリスト直（本案）** | 低 | ¥0 | 中〜高 | ◎ MSAL認証・Graph呼出コードを流用 | **採用** |
| B. Google Apps Script + スプレッドシート | 低 | ¥0 | 高（サーバ側で全検証） | △ 認証系を作り直し | 次点 |
| C. Supabase (Postgres + RLS) | 中 | ¥0〜 | 高 | × 全面新規 | 将来の移行先 |
| D. Power Automate HTTPトリガー経由 | 中 | Premiumライセンス必要 | 高 | ○ | コスト理由で見送り |

**A案を採る理由**
1. 既存 `index_b.html` に MSAL 認証と Graph API 呼び出しが完成しており、丸ごと再利用できる。社員は既に持っている M365 アカウントでログインでき、**新しいID・パスワードの配布が不要**。
2. 追加のサーバ・ライセンス費用がゼロ。
3. 改ざん耐性は SharePoint の標準機能で確保できる（次項）。

### 2.2 改ざん防止の仕掛け（A案の要）

クライアント（ブラウザ）から直接 Graph API を叩く構成の弱点は「端末側で好きな値を送れる」ことです。これを SharePoint の標準機能だけで塞ぎます。

| 対策 | 実装 |
|------|------|
| **打刻時刻の偽装** | 時刻の正は SharePoint が自動採番する `Created` 列（サーバ時刻・書込不可）。端末が送った時刻は `ClientTime` 列に別途保存し、差が5分以上なら `要確認` フラグ |
| **他人になりすまして打刻** | 打刻者の正は `Author` 列（ログインユーザーからサーバが自動採番・書込不可）。端末が送った社員IDと不一致なら拒否 |
| **過去の打刻の書き換え** | `PunchLogs` リストの権限を **「アイテムの追加のみ」**（投稿権限＋「アイテムの編集：なし」）に設定。従業員は自分の打刻を作成できるが、作成後は誰も編集・削除できない |
| **他人の打刻の閲覧** | リスト詳細設定で **「アイテムの表示：ユーザーが作成したアイテムのみ」** に設定。管理者グループのみ全件閲覧可 |
| **位置の偽装（GPSスプーフィング）** | Webからは完全な検知不可。多層で緩和：①IP判定との突合 ②`coords.accuracy` の異常値検知 ③前回打刻からの移動速度が物理的に不可能なら要確認フラグ |

> **設計判断**: 位置の偽装は完全には防げません。しかしこれは「不正を機械的にブロックする」システムではなく「**不正を後から確実に検出でき、抑止力として機能する**」システムとして設計します。全打刻に位置・IP・時刻差・作成者が記録され監査可能な状態にあること自体が抑止力になります。厳密なブロックが必要になった段階で B案／C案のサーバ側検証へ移行します。

## 3. 位置記録の設計

### 3.1 取得手段の比較（現実に何ができるか）

| 手段 | 精度 | Webブラウザから | 備考 |
|------|------|----------------|------|
| GPS（`enableHighAccuracy: true`） | 屋外 5〜50m | ○ 要許可（初回のみ） | 屋内・ビル影で劣化 |
| Wi-Fi測位 | 20〜100m | ○ 同じAPIが自動フォールバック | 屋内で有効。周辺APのDB照合 |
| 携帯基地局測位 | 100m〜2km | ○ 同じAPIが自動フォールバック | 最終手段。市区町村レベル |
| **基地局ID・電波強度の直接取得** | — | **× 不可** | ブラウザに API が存在しない。iOSはネイティブでも禁止 |
| グローバルIPアドレス判定 | 事業所単位 | ○ **許可不要・自動** | 会社Wi-Fi接続なら「社内」と確実に判定できる |
| BLEビーコン | 屋内 1〜5m | △ Web Bluetooth は要ユーザー操作、iOS Safari非対応 | 実用にはネイティブアプリが必要 |
| NFCタグ | ピンポイント | △ Web NFC は Android Chrome のみ | タグにかざす操作が必要 |

**採用**: `Geolocation API`（GPS／Wi-Fi／基地局を OS が自動で使い分ける）＋ `グローバルIP判定` の二段構え。BLE／NFC はネイティブアプリ化する場合の将来拡張とします。

### 3.2 「裏で」記録するとはどういうことか

ブラウザの仕様上、位置情報は**必ず**ユーザーの明示的な許可が要ります。これは回避できません。ただし許可は**サイト単位で一度きり**で、以降はダイアログが出ません。したがって実運用は次のようになります。

```
【初回のみ】
  ログイン
   → 利用目的の説明画面（「打刻の瞬間だけ位置を記録します。常時追跡はしません」）
   → [同意する] タップ
   → ブラウザの許可ダイアログ → [許可]
   → 同意記録を Employees リストに保存（同意日時つき）

【2回目以降 = 日常の打刻】
  アプリを開く → [出勤] を1タップ
   → 位置は自動取得（ダイアログなし・従業員の追加操作ゼロ）
   → 完了表示
```

つまり**日常の操作としては完全に「裏で」動きます**。従業員が意識するのは初回の一度だけです。

### 3.3 打刻フロー（位置取得のタイムアウト設計）

```
[出勤] タップ
  │
  ├─ 端末時刻を記録
  │
  ├─ navigator.geolocation.getCurrentPosition()
  │     enableHighAccuracy: true
  │     timeout: 8000ms         ← 8秒で打ち切る
  │     maximumAge: 30000ms     ← 30秒以内のキャッシュは再利用（高速化）
  │
  ├─ 【成功】 緯度・経度・精度(m) を取得
  │     └→ ジオフェンス判定（§3.4）
  │
  ├─ 【拒否 / 失敗 / タイムアウト】
  │     └→ 位置なしで続行。LocationStatus = "拒否" / "失敗" / "タイムアウト"
  │        ★ 打刻自体は必ず成功させる（労働時間の記録欠落を作らない）
  │
  ├─ PunchLogs に POST（サーバ時刻 Created が打刻時刻の正）
  │
  ├─ 【通信失敗】 IndexedDB にキューイング → Service Worker が復帰時に自動送信
  │
  └─ 完了表示「08:52 出勤しました ／ 場所: 本社」
```

**重要な設計判断**: 位置が取れなくても打刻は通します。位置取得の失敗を理由に打刻をブロックすると、労働時間の客観的記録が欠落し、かえって労基法違反のリスクを生むためです。位置なし打刻は管理画面で `要確認` として一覧されます。

### 3.4 ジオフェンス判定

`Sites` マスタに事業所・現場を緯度経度＋半径で登録し、打刻位置と照合します。

```javascript
// 2点間距離（Haversine公式・単位m）
function distanceM(lat1, lon1, lat2, lon2) {
  const R = 6371000, toRad = d => d * Math.PI / 180;
  const dLat = toRad(lat2 - lat1), dLon = toRad(lon2 - lon1);
  const a = Math.sin(dLat/2) ** 2
          + Math.cos(toRad(lat1)) * Math.cos(toRad(lat2)) * Math.sin(dLon/2) ** 2;
  return 2 * R * Math.asin(Math.sqrt(a));
}

// 判定：測位誤差を半径に加算して甘めに判定する
function judgeSite(lat, lon, accuracy, sites) {
  let best = null;
  for (const s of sites) {
    const d = distanceM(lat, lon, s.Lat, s.Lon);
    const margin = s.RadiusM + Math.min(accuracy || 0, 200); // 誤差は最大200mまで加味
    if (d <= margin && (!best || d < best.dist)) {
      best = { site: s, dist: d };
    }
  }
  return best
    ? { name: best.site.Title, status: '圏内', dist: Math.round(best.dist) }
    : { name: '事業所外', status: '圏外', dist: null };
}
```

| 判定結果 | 記録される値 | 管理画面での扱い |
|---------|-------------|----------------|
| 登録地点の半径内 | `本社` `〇〇霊園` 等 | 通常表示 |
| どの地点からも外 | `事業所外` | ⚠️ 要確認フラグ |
| 位置取得できず | `位置なし` | ⚠️ 要確認フラグ |
| 精度500m超 | 地点名＋`精度低` | ⚠️ 要確認フラグ |
| 前回打刻から移動速度 >150km/h | 地点名＋`移動異常` | 🚩 不正の疑い |

> 石材業は霊園・寺院での現場作業が多いため、`Sites` マスタには本社・作業場に加えて主要な取引先霊園（慈光寺・長善寺・福寿院・光明院 等、既存 `data_*.js` の寺院データと対応）を登録しておくと、現場打刻がそのまま「どの現場にいたか」の記録になります。

## 5. 有給休暇の計算ロジック（労基法39条）

### 5.1 付与日数（通常付与）

週所定労働日数5日以上、**または**週所定労働時間30時間以上の労働者。

| 継続勤務年数 | 6ヶ月 | 1年6ヶ月 | 2年6ヶ月 | 3年6ヶ月 | 4年6ヶ月 | 5年6ヶ月 | 6年6ヶ月以降 |
|---|---|---|---|---|---|---|---|
| 付与日数 | 10 | 11 | 12 | 14 | 16 | 18 | **20** |

### 5.2 付与日数（比例付与）

週所定労働日数4日以下 **かつ** 週所定労働時間30時間未満のパート・アルバイト。

| 週所定日数 | 年間所定日数 | 6ヶ月 | 1.5年 | 2.5年 | 3.5年 | 4.5年 | 5.5年 | 6.5年〜 |
|---|---|---|---|---|---|---|---|---|
| 4日 | 169〜216日 | 7 | 8 | 9 | 10 | 12 | 13 | 15 |
| 3日 | 121〜168日 | 5 | 6 | 6 | 8 | 9 | 10 | 11 |
| 2日 | 73〜120日 | 3 | 4 | 4 | 5 | 6 | 6 | 7 |
| 1日 | 48〜72日 | 1 | 2 | 2 | 2 | 3 | 3 | 3 |

```javascript
const GRANT_FULL = [10, 11, 12, 14, 16, 18, 20];
const GRANT_PRO = {
  4: [7, 8, 9, 10, 12, 13, 15],
  3: [5, 6, 6,  8,  9, 10, 11],
  2: [3, 4, 4,  5,  6,  6,  7],
  1: [1, 2, 2,  2,  3,  3,  3],
};

/**
 * @param {number} yearsIndex 勤続インデックス（0=6ヶ月, 1=1.5年, … 6以上=6.5年〜）
 * @param {number} weeklyDays 週所定労働日数
 * @param {number} weeklyHours 週所定労働時間
 * @param {number} attendRate 出勤率(0〜1)
 */
function grantDays(yearsIndex, weeklyDays, weeklyHours, attendRate) {
  if (attendRate < 0.8) return 0;              // 出勤率8割未満は付与なし
  const i = Math.min(yearsIndex, 6);
  const isPro = weeklyDays <= 4 && weeklyHours < 30;
  return isPro ? (GRANT_PRO[weeklyDays]?.[i] ?? 0) : GRANT_FULL[i];
}
```

### 5.3 出勤率の計算

`出勤率 = 出勤日数 ÷ 全労働日`

次の日は**出勤したものとみなす**（分子に算入）。
- 業務上の負傷・疾病による療養のための休業期間
- 産前産後の休業期間
- 育児休業・介護休業期間
- 年次有給休暇を取得した日

### 5.4 消化・繰越・時効

- **時効は2年**（労基法115条）。付与日から2年で未消化分は消滅します。2020年改正で賃金請求権は3年になりましたが、年休は2年のままです。
- **繰越**：前年度の未消化分は翌年度に繰り越されます。したがって最大保有日数は 20 + 20 = **40日**。
- **消化順序**：本設計では **FIFO（古い付与分から消化）** とします。法律上は消化順の定めがなく就業規則によりますが、繰越分から消化する方が労働者に有利で、失効も減るため一般的です。就業規則にその旨を明記してください。

```javascript
/** 有給を FIFO（失効が近い順）で消化する */
function consumeLeave(grants, days, leaveDate) {
  const alive = grants
    .filter(g => g.GrantDate <= leaveDate && leaveDate < g.ExpireDate)
    .sort((a, b) => a.GrantDate - b.GrantDate);   // 古い順＝失効が近い順

  let rest = days;
  const applied = [];
  for (const g of alive) {
    if (rest <= 0) break;
    const avail = (g.GrantDays + g.CarryOverDays) - g.UsedDays;
    if (avail <= 0) continue;
    const use = Math.min(avail, rest);
    applied.push({ grantId: g.Id, days: use });
    rest -= use;
  }
  if (rest > 0) throw new Error(`有給残日数が不足しています（不足 ${rest} 日）`);
  return applied;
}
```

### 5.5 年5日の取得義務（F-15）

年10日以上の年休が付与された労働者には、**付与日から1年以内に5日**を取得させる義務があります。違反は労働者1人につき30万円以下の罰金（労基法120条）。

システムは次のアラートを出します。

| タイミング | アラート |
|-----------|---------|
| 付与日から6ヶ月経過 | 消化2日未満の社員を黄色警告 |
| 付与日から9ヶ月経過 | 消化3日未満の社員を橙色警告 |
| 付与日から10ヶ月経過 | 消化5日未満の社員を**赤色警告**＋使用者による時季指定を促す |
| 管理画面トップ | 期限までの残月数と未消化日数を常時表示 |

半日単位の取得は0.5日として通算されますが、**時間単位年休は年5日義務の日数には算入されません**（この判定はロジックに明記）。

### 5.6 基準日の統一（斉一的取扱い）

入社日ごとに基準日がバラバラだと管理が煩雑なため、全社員の基準日を統一する運用（例：毎年4月1日）も選択できるようにします。ただし**法定の付与日を前倒しすることは可、後ろ倒しは不可**です。統一時は入社日から最初の基準日までの期間を按分して付与します。設定で「入社日基準」「全社統一基準日」を切替可能とします。

## 6. プライバシー設計

位置情報は個人情報保護法上の個人情報にあたります。従業員の位置を記録するシステムは、設計だけでなく**運用の整備**が必須です。

### 6.1 システム側の措置

| 原則 | 実装 |
|------|------|
| **打刻時のみ取得** | 常時追跡は行いません。`watchPosition()` は使用せず、打刻イベント時の `getCurrentPosition()` のみ |
| 利用目的の明示 | 初回ログイン時に説明画面を表示し、同意を `Employees.ConsentDate` に記録 |
| 最小限の取得 | 緯度・経度・精度のみ。速度・高度・移動履歴は取得しない |
| 閲覧制限 | 従業員は自分の記録のみ閲覧可（SharePointのアイテムレベル権限）。管理者のみ全件閲覧 |
| 保存期間 | 打刻記録は法定保存期間（5年／当面3年）経過後に緯度経度のみ削除するバッチを用意 |
| 透明性 | 従業員は自分の打刻位置を地図でいつでも確認できる（自分に何が記録されているか見える） |

### 6.2 運用側で必要な整備（システム外の宿題）

- [ ] **就業規則への記載**：打刻時に位置情報を取得すること、その目的（勤務地の確認・労働時間の適正把握）、保存期間、閲覧範囲
- [ ] **従業員への事前説明と書面同意**の取得
- [ ] 個人情報の利用目的の公表（個人情報保護法21条）
- [ ] 位置情報を人事評価に直接用いない旨の明確化（用いる場合はその旨を事前明示）
- [ ] 私用端末（BYOD）を使う場合の通信費負担・端末管理の取り決め

> これらを整えずに位置記録を開始すると、プライバシー侵害としての紛争リスクがあります。**システムの実装より先に就業規則の改定を行ってください。**

## 付録A. 打刻処理の実装スケッチ

```javascript
const GEO_OPTS = { enableHighAccuracy: true, timeout: 8000, maximumAge: 30000 };

/** 位置を取得する。失敗しても reject せず、状態を返す */
function getLocation() {
  return new Promise(resolve => {
    if (!navigator.geolocation) {
      return resolve({ status: '失敗', reason: '非対応端末' });
    }
    navigator.geolocation.getCurrentPosition(
      pos => resolve({
        status: '取得成功',
        lat: +pos.coords.latitude.toFixed(6),
        lon: +pos.coords.longitude.toFixed(6),
        accuracy: Math.round(pos.coords.accuracy),
        // 精度が数十m以内ならGPS、粗ければWi-Fi/基地局と推定
        source: pos.coords.accuracy <= 50 ? 'GPS' : 'ネットワーク',
      }),
      err => resolve({
        status: err.code === err.PERMISSION_DENIED ? '拒否'
              : err.code === err.TIMEOUT          ? 'タイムアウト'
              : '失敗',
        reason: err.message,
      }),
      GEO_OPTS
    );
  });
}

/** 打刻本体。位置取得の成否にかかわらず必ず打刻を記録する */
async function punch(punchType) {
  lockButton();                                  // 二重打刻防止
  const clientTime = new Date().toISOString();

  const loc = await getLocation();               // 最大8秒
  const site = loc.lat
    ? judgeSite(loc.lat, loc.lon, loc.accuracy, await loadSites())
    : { name: '位置なし', status: '不明', dist: null };

  const record = {
    Title:          currentEmployee.empNo,
    PunchType:      punchType,
    WorkDate:       resolveWorkDate(clientTime),  // 深夜勤務は前日扱い
    ClientTime:     clientTime,
    Lat:            loc.lat ?? null,
    Lon:            loc.lon ?? null,
    AccuracyM:      loc.accuracy ?? null,
    LocationStatus: loc.status,
    LocationSource: loc.source ?? '不明',
    SiteName:       site.name,
    SiteDistM:      site.dist,
    UserAgent:      navigator.userAgent,
  };

  try {
    // Created（サーバ時刻）と Author（ログインユーザー）は SharePoint が自動採番する
    const saved = await graphPost('PunchLogs', record);
    flagIfSuspicious(saved, record);             // 時刻差・圏外・移動異常の判定
    showSuccess(punchType, saved.Created, site.name);
  } catch (e) {
    await queueOffline(record);                  // IndexedDB に退避
    showPending(punchType);                      // 「圏外のため保留中」
  } finally {
    unlockButton();
  }
}
```

## 付録B. SharePoint リストの権限設定手順

`PunchLogs` リスト → 設定 → 詳細設定：

| 設定項目 | 値 | 効果 |
|---------|----|------|
| アイテムに対する権限 → 読み取りアクセス | **ユーザーが作成したアイテムのみ** | 従業員は他人の打刻を見られない |
| アイテムに対する権限 → 作成/編集アクセス | **アイテムの作成のみ（編集不可）** | 作成後の書き換えを禁止 |
| 添付ファイル | 無効 | 不要なデータ混入を防ぐ |
| バージョン履歴 | 有効（管理者による修正の追跡用） | 監査証跡 |

管理者グループには別途「フルコントロール」を付与し、全件閲覧と修正を可能にします。
